# Applications SDK — Domain Model

**Status:** Implemented · **Date:** 2026-07-25 · **Owner:** Tensorlake · **Scope:** Applications SDK

This page defines the public entities exposed by the Applications SDKs. Their language-neutral
shapes are formalized in [canonical-types.schema.json](canonical-types.schema.json).

---

## Identifier scheme

Application and function names are stable identifiers within an application namespace. Request,
future, and durable-call IDs are opaque strings generated by the platform or SDK.

| Identifier | Scope |
|---|---|
| Application name | Deployment namespace |
| Function name | Application |
| Application version | Deployed application revision |
| Request ID | Application request |
| Future or durable-call ID | Request |

TypeScript schema-free registrations require an explicit stable name because bundled function names
can change. Explicit-schema registrations can use `options.name` or a non-anonymous handler name.
Python names derive from function or qualified class-method names.

## Entities

### Application

An application is a registered function with entrypoint configuration: tags, default retries,
optional region, and generated version. It is the public remote API boundary and provides default
retry policy to functions that do not override it.

### Function

A function pairs a handler with description, resource limits, image, secrets, retry override,
region, and container-pool settings. Python can attach class metadata; TypeScript pairs the handler
with parameter and return schemas.

### Future

A Future represents a computation that starts explicitly, on result access, or on await. It tracks
completion, result or typed exception, and optional delayed start. A Future starts once and can be
observed more than once after completion.

### Registered function callable

Calling a registered function runs locally when no durable runtime exists and creates a durable
child call when invoked inside an allocation. The callable also exposes factories or methods for
Future, map, reduce, and tail-call composition.

### Request

A Request represents one application invocation. It carries a request ID and exposes output
retrieval. Remote requests poll or stream server state. TypeScript local requests also expose
`cancel()`, which aborts their request-context signal and rejects pending output.

### Request context

Request context contains request ID, state, metrics, and progress. TypeScript additionally exposes
an `AbortSignal`. Context access outside a running function raises `SDKUsageError`.

### File

A File is application data represented by bytes and content type. Serialization boundaries copy
its content; the object itself does not promise deep immutability. TypeScript uses a process-global
brand so Files created by another bundled SDK copy retain `instanceof` behavior.

### Error

The public hierarchy distinguishes SDK misuse, serialization, deserialization, function failure,
timeout, request-directed failure, remote API failure, replay mismatch, and internal runtime failure
where supported by the language.

## Lifecycles

### Definition

```text
module load -> registered -> validated -> manifest generated -> bundled/deployed
```

Python defers most validation to deployment for decorator ergonomics. TypeScript validates
registration shape, options, schemas, and defaults when the registration is created. It verifies
that the handler returned a Promise when the handler is invoked.

### Future

```text
created -> running -> succeeded
                   -> failed
```

`run` or delayed run can transition a Future once. Await and result access start an unstarted
Future. Wait operations start all supplied Futures and return completed and incomplete partitions.

### Request

```text
submitted -> running -> success
                     -> failure
                     -> cancelled (local TypeScript)
```

Request-level `RequestError` preserves the user message and remains distinct from ordinary function
failure.

## Assumptions and open questions

**Assumptions**

- Function and application names remain stable for the lifetime of a deployed version.
- Request state is scoped by the orchestration server to one application request.

**Decisions**

- *Future start.* **Single transition to running.** Duplicate starts are SDK misuse rather than
  duplicate durable calls.
- *File identity.* **Direct boundary value.** Nested Files are rejected where the JSON value model
  cannot preserve their raw-byte identity.
- *Request error.* **Separate terminal category.** User-directed request failure is catchable by a
  parent and preserves its exact payload.
